Website Review — internal

How the tool is built & what's next. Not linked anywhere; reveal with #build in the URL.

HIDDEN · INTERNAL

A reviewer annotates a live site through a share-link. Their notes land in Supabase, sync down into a file Claude reads, and become edits to the site that you approve — then "resolved" flows back so the reviewer sees it. That round-trip is the whole product.

Where it can live (hosting)

🅖
Inside a GHL page (recommended for GHL sites)
Inline the whole widget into the site's GHL Custom-HTML embed — no separate file host. Dormant for visitors; wakes on ?review=KEY. One paste per client account.
📄
Static host (GitHub Pages)
For non-GHL sites: host embed.js + config.js and reference by <script src>.

The pieces

embed.js widget

One script you paste (or inline) into any site you control. Shadow-DOM (can't collide with the host), RTL-aware. Stays dormant until the page is opened with ?review=KEY. Draws the pins, composer & notes list.

config.js keys

Supabase URL + the publishable key (browser-safe). The one file you edit to point the tool at your Supabase.

Supabase backend

Tables projects / notes / comments / attachments, RLS scoped by the x-board-key header, and a public-read review-photos bucket. One project serves every client board.

sync.mjs bridge

~30-line Node script. pull → writes feedback.json/.md + downloads photos. --push → sends resolved status back up. Uses only the public key. (Phase 3)

feedback.md / .json the handoff

Lives inside the reviewed site's repo. .json is the source of truth; .md is the human/Claude-readable mirror, grouped by section. (Phase 3)

Claude Code the doer

Reads feedback.md, locates each note by its section id + quoted text, and proposes a real diff to index.html for your approval.

How a note finds its spot (anchoring)

①
Nearest section id
The pin latches onto the closest ancestor with an id — #about, #process… The Ruth site has clean ones, so Claude knows exactly which section.
②
Verbatim quoted text
For highlights: the exact selected words (+ a little surrounding text). Survives layout changes and maps straight to "change this sentence."
③
Fractional position
x/y as a fraction of the anchor box, so a pin dropped on mobile still lands right on desktop.
⚑
Can't resolve? Parked.
If the target is genuinely gone, the note goes to a "needs re-anchor" tray — never silently mis-placed.

We deliberately don't stamp hidden ids into the page — a static index.html never gets them back on disk, so Claude would never see them. Section id + exact quote are the anchors that actually survive Claude editing the file.

Access & security

🔑
Capability link, no login
The project key in ?review=… is the credential — treat the link like a password. Reused from the HomeApp board model.
🛡️
RLS is the whole boundary
Every row is scoped to its project key; a wrong key sees zero rows (verified). The publishable key is public by design.
⚠️
Honest limit
One key per project → the tool can't yet tell "owner" from "reviewer" server-side. Fine for a founder + a few trusted reviewers; upgrade path is Supabase Auth.
